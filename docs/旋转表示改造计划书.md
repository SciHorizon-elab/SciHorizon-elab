# SciHorizon-ELAB 旋转表示改造评估计划书

> **方案名称**:H5 waypoint 旋转表示从 euler(xyz) 切换为 axis-angle / rotation vector(rotvec)
> **目标**:根除 ±π 边界假跳变 + unwrap 补丁失效造成的 pi05 训练目标污染
> **当前主干**:euler('xyz') 3 维 + unwrap_euler_sequence 补丁 + DeltaActions(无 wrap,29.1% 基线)
> **改后主干**:rotvec 3 维(rotvec 维度=3,与 euler 维度一致,**所有下游维度/feature 名/schema 不变**)+ 无 unwrap + **RLDSDeltaActions/RLDSAbsoluteActions(带 ±π wrap,必做)**
>
> **修订版 v2(2026-09-24)**:经严格核对后修订。三处关键修订:
> ① 绝对 rotvec 在 180° 边界仍有 ±2π 假跳变(倒置抓取姿态恰贴边界),wrap 必做;
> ② 补全 eval 侧文件清单(dm_env.py / evaluator/base.py / 6 个 policy 文件);
> ③ quat 分量序约定(wxyz vs xyzw)显式化 + ee_state 新旧双格式处理 + 表示版本标记。

---

## 0. 背景与因果链(简要)

`scripts/convert_to_lerobot_pi.py` 里的 `unwrap_euler_sequence` 是一个**事后补丁**,目的
是消除 euler 在 ±π 边界的 2π 假跳变。在我们之前用 `tmp/check_euler_unwrap.py` 跑的实测
中确认了两个事实:

1. 同一 episode 里,state(物理仿真反馈)和 action(waypoint 规划)的 euler 序列**在
   ±π 边界跳变位置不对齐**——它们来自不同代码路径(`get_observation` vs skill 库)。
   实测:data_0.hdf5 中 state 仅 2 次跳变(188/205 帧,均为 ~3.5 rad 物理真实旋转),
   action 有 8 次跳变(61/66/143/173/187/204/214/310 帧,其中 6 次为精确 ±2π 表示跳变),
   位置几乎不重合。
2. unwrap 算法对"同一序列内反复穿越 ±π"会进入错位分支(累积偏移自相矛盾)。
   实测:unwrap 后 euler delta 仍有 max 4.86 rad(> π),|delta|>π 的帧仍有 20+ 个。

后果链:
```
wrap 错的 euler action 写入 LeRobot
  → 训练 transform DeltaActions 用 state 减 action
  → delta 在 euler 3:6 维存在系统性污染
  → 模型学到错误的姿态变化方向
  → 推理 wrap 到错误分支,任务失败
```

## 2. 各问题解决程度评估

### 2.1 🔴 v2 修订:rotvec 的 180° 边界跳变——wrap 必做的数学依据

v1 声称"rotvec 区间 [-π,π],无 ±π 多值,根除跳变"。**这不成立**:

rotvec 映射是 SO(3) → 半径 π 的实心球,边界球面上 **`+π·n̂` 与 `−π·n̂` 是同一个旋转**
(绕 n̂ 转 +180° 与 −180° 等价)。物理姿态连续穿越 180° 区域时,绝对 rotvec 从
`+π·n̂` 跳到 `−π·n̂`,产生 ~2π 假跳变——**与 euler ±π 边界问题同构**,只是边界从
立方体面换成了球面。

而本项目主工作姿态恰在边界上:unwrap 补丁 docstring 自述"机械臂 roll 物理上钉在
±π 边界(**倒置抓取姿态**)"——倒置 ≈ 绕水平轴 180° ≈ rotvec 贴着边界球面。

**因此**:
- waypoint/H5 里的**绝对 rotvec** 在倒置段仍会 ±2π 翻转 → 无法靠换表示根除;
- 但 **delta(target − state)经 wrap 后可以根除**:真实单步旋转 < 0.3 rad(plan 实测),
  wrap `(d + π) % 2π − π` 精确恢复真实增量;
- `RLDSDeltaActions/RLDSAbsoluteActions` 已带此 wrap → **换用它们是必做项**(§1.3);
- 残留:state(输入端)的绝对 rotvec 仍可能在边界抖。这与 train/eval 一致(env 端同样
  直出),输入端噪声比 target 端污染危害低,接受;§5.4 验收时实测翻转率确认影响。

### 2.2 问题解决度对照表(v2 修订)

| 问题 | 现状 | rotvec + wrap 方案 | 备注 |
|---|---|---|---|
| ±π 边界 2π 假跳变(target 侧) | 严重 | ✅ 根除(wrap 后 delta 干净) | 改前实测 unwrap 后仍有 4.86 rad 巨值 |
| 绝对 rotvec 180° 边界翻转 | –(新表示) | ⚠️ 存在但被 wrap 化解(target 侧);state 侧残留噪声 | §2.1 论证;验收时实测翻转率 |
| unwrap 错位累积偏移 | 严重 | ✅ 根除(补丁删除) | 算法本身删掉 |
| state/action 跳变不对齐 | 中 | ✅ 根除(不再依赖 unwrap 对齐) | wrap 在 transform 端逐帧做,无序列依赖 |
| euler 减法 ≠ 真实旋转差 | 严重 | ⚠️ 缓解:rotvec 减法+wrap 在小角度下是 geodesic delta 的高阶近似 | 单步 <0.3 rad 时误差 ≈ δ²/2 ≈ 0.045 rad ≈ 2.6°,可接受;根治需 quat log(§1.8) |
| norm_stats 在环形量上无意义 | 中 | ⚠️ 缓解:rotvec 连续性更好,但绝对 rotvec 在倒置段仍双峰 | z-score 对双峰仍有偏,但比 euler 的 ±π 多值好;留待 diag 观测 |
| 模型对带 2π 噪声的监督目标过拟合 | 严重 | ✅ 根除 | |
| 双覆盖(quat 专属) | 不存在 | ✅ 仍不存在 | 避开 quat 方案 |
| 预训练先验契合(LoRA pi05) | – | ✅ rotvec 是 pi05/libero 官方原生动作表示(obs 侧 `_quat2axisangle`,输出 delta rotvec 直接执行) | 0 适应成本 |
| **eval/train 表示错配(v1 未覆盖)** | – | ✅ eval 侧全量同步改(§1.4) | dm_env 直出 rotvec,policy 消费 rotvec,IK 端 rotvec→quat(wxyz) |

**残留问题**(rotvec + wrap 改完后仍然存在):

1. **state 输入端的绝对 rotvec 边界翻转**:倒置段 state 的 rotvec 仍可能 ±2π 抖动。
   train/eval 两端一致(env 直出),且 proprio 是辅助输入,危害远低于 target 污染。
   验收时用 diag 实测翻转率,若过高再议(可对 state 也做逐帧 unwrap 的 rotvec 版,
   属后续优化)。
2. **小角度近似**:rotvec 减法+wrap 在单步 <0.3 rad 下误差 ≈2.6°。高精度任务需
   quat geodesic delta(§1.8)。
3. **norm_stats 的双峰残留**:倒置段绝对 rotvec 双峰,z-score 有偏。留 diag 观测。
4. **相机/skill/gripper 那一摊老问题**(second_image 与 wrist_image 重复用 rgb[3]、
   `transformers`/lerobot 老版本兼容等)——与本次改动无关,本来就有,不动。

## 6. 替代方案对比(已排除)

| 方案 | 不选的原因 |

| **保留 euler + 改进 unwrap(state/action 对齐)** | diag_delta_distribution.py 里的 `new_offset_wrap` 方案;零数据成本吃一部分收益,但 unwrap 算法对反复穿越的根本缺陷仍在 |
